RLS e funções de permissão

Schema private não é exposto pela API do Supabase. Funções SECURITY DEFINER, STABLE, SET search_path = '', com nomes totalmente qualificados.

private.has_org_role(org uuid, roles text[]) → boolean
  -- auth.uid() tem um dos papéis na organização

private.can_read_team(team uuid) → boolean
  -- staff do time (qualquer papel) OU owner/admin da organização do time

private.can_write_team(team uuid, roles text[] default '{coach}') → boolean
  -- time active E (papel do time em roles OU owner/admin da organização)

-- Uso nas policies (o select faz o Postgres calcular uma vez por consulta):
create policy events_read on public.events for select to authenticated
  using ((select private.can_read_team(team_id)));
create policy events_write on public.events for all to authenticated
  using ((select private.can_write_team(team_id)))
  with check ((select private.can_write_team(team_id)));

RPCs (Postgres)

Todas SECURITY INVOKER (o RLS do usuário vale dentro delas), exceto accept_invitation e create_organization, que precisam criar o primeiro vínculo e por isso validam tudo internamente.

RPC team_dashboard(p_team uuid) → jsonb

Uma ida ao banco por dashboard: elenco por posição, disponíveis, próximos 3 eventos, últimos 5 resultados, aproveitamento, saldo, líderes (top 3 das estatísticas-chave do esporte), médias de altura/idade (sem datas).

RPC athlete_season_stats(p_team uuid, p_from date default null) → table

Totais e médias por atleta × estatística; base do ranking e do overall calculado no módulo do esporte.

RPC save_lineup(p_event uuid, p_formation text, p_slots jsonb) → uuid

Transação: upsert de lineups, apaga e reinsere lineup_slots. Valida membro ativo e sem repetição.

RPC save_match_result(p_event uuid, p_our int, p_their int, p_periods jsonb)

Upsert do resultado e events.status = 'done'. Formato dos períodos validado antes na API pelo módulo do esporte.

RPC save_match_stats(p_event uuid, p_athlete uuid, p_stats jsonb)

Upsert de todas as chaves do atleta no jogo; chave com valor 0 é removida (menos linhas).

RPC accept_invitation(p_token text) → jsonb

Compara sha256; checa pending, validade e e-mail do usuário; cria o papel; marca accepted; audita. Tudo numa transação.

B · API (Next.js Route Handlers)

Comum a todas as rotas de escrita: checagem de Origin (CSRF) → getUser() → parse com allowlist → validação do módulo do esporte → RPC/tabela com a sessão do usuário. Respostas: 400 validação · 401 sem sessão · 403 origem · 404 não existe ou sem permissão · 409 conflito · 422 regra do esporte (lista de problemas) · 503 banco indisponível. Logs sem dados pessoais. PUT são idempotentes.

POST /api/teams · owner/admin

{"name":"Falcons Futsal","sport":"futsal","category":"male","color":"#22c55e"}

201 {"id":"…","slug":"falcons-futsal"} · 409 slug em uso.

PATCH /api/teams/:teamId · owner/admin

Nome, cor, categoria, status. Troca de sport → 409 se houver dados.
